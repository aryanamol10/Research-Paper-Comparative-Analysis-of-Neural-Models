\subsection{The Control Pair: Identical Math, Different Code}
\label{sec:res-control}
\ifcompact
Sequential and Modular compute the same function and produce identical test MSE; their training step times
differ by \ctrlStepGap\%, so the pilot's \pilotSpeedup$\times$ ``Modular advantage'' (\cref{sec:pilot}) disappears. Their batch-1
latency differs by \ctrlLatGap\% (non-overlapping 95\% intervals) because Sequential's container makes \modSequential\
\texttt{nn.Module} calls against Modular's \modModular: code organization alone costs time.
\else
Sequential and Modular compute the same function and, under the same seed, produce the same test MSE on every
task (\cref{tab:main}). Their training step times differ by only \ctrlStepGap\%, confirming that the pilot's
\pilotSpeedup$\times$ ``Modular advantage'' (\cref{sec:pilot}) disappears once the framework and training loop
are held constant. Their batch-1 inference latency, however, differs by \ctrlLatGap\% (\latOneSequential\ vs.\
\latOneModular\us), with non-overlapping 95\% intervals across ten shuffled repeats, so the gap is not run-order
noise. Both dispatch three tensor operations, but Sequential's \texttt{nn.Sequential} container makes
\modSequential\ \texttt{nn.Module} calls per forward pass against Modular's \modModular\ifcompact.\else. The control
pair therefore isolates a second, purely software overhead, showing that code organization costs time even when the
math is the same (\cref{sec:res-latency}).\fi
\fi

\subsection{Accuracy: Structure Pays Off Only When the Task Has Structure}
\label{sec:res-acc}
\textbf{Linear and curved tasks.} Every model reaches the noise floor on the linear task (MSE 1.02--1.03 against a
floor of 1, $R^2\approx0.97$), and on the curved task every model finishes within 2\% of the floor of 4. Simple
targets leave nothing for topology to improve upon, so at a 385-parameter budget the arrangement of parameters does
not change the final accuracy. With standardized targets, every model also converges quickly, on average within 10 epochs.

\textbf{Chained task.} Here topology matters, but only for the hybrid built for it. \HB, whose modules mirror the
three stages of the target, reaches \mseChainHB\ test MSE, \chainHBGain\% below Sequential (\mseChainSequential;
$p<0.05$), and its excess error over the noise floor of 0.25 (\chainExcessHB) is \chainExcessRatio$\times$ smaller
than Sequential's (\chainExcessSeq). \HA, which has no knowledge of the stages, only matches Sequential
(\mseChainHA), and plain breadth does not help: Parallel is the worst model (\mseChainParallel).

\ifcompact
\textbf{Undertraining or a ceiling?} Trained for 300 epochs (\cref{fig:long}), every model improves (Sequential to \longSeqThree), but
\HB still ends \longHBGain\% lower (\longHBThree; $p=\longHBpval$), so the gap is not an artifact of the 100-epoch budget.
\else
\textbf{Undertraining or a ceiling?} At 100 epochs the chained-task models are still improving, so we trained
Sequential, Parallel, \HA, and \HB for 300 epochs (\cref{fig:long}). Every model improves:
Sequential falls \longSeqDrop\% to \longSeqThree, and Parallel (\longParThree) catches up with it. The \HB advantage
persists: it ends at \longHBThree, \longHBGain\% below Sequential ($p=\longHBpval$), with \longExcessRatio$\times$
smaller excess error. Gains level off late (the last 1\% improvement comes after epoch \longHBPlateau\ for \HB and
\longSeqPlateau\ for Sequential, on average), so these values are close to each model's ceiling at this budget. The
gap is not an artifact of the 100-epoch training budget.
\fi

\subsection{Latency: Operator Count, Not Parameter Count}
\label{sec:res-latency}
\Cref{tab:arch} and \cref{fig:ops} show that, at a nearly constant parameter budget, single-sample inference
latency spans almost 4$\times$, from \latOneModular\us (Modular) to \latOneHB\us (\HB). Parameter count
cannot explain this: all models have 385--387 parameters. Neither can MACs: Parallel and Sequential have the
same 256 MACs, but Parallel is slower, and \HC has the most MACs (350) but is faster than \HA and \HB. What does
explain it is the number of tensor operations dispatched per forward call. A linear fit of batch-1 latency on
operation count gives $R^2=\opsFitRsq$ with a slope of about \opsFitSlope\us per operation. At this scale, each
\texttt{Linear}, \texttt{ReLU}, \texttt{cat}, or add pays a fixed framework dispatch cost that dwarfs its
arithmetic. \HB has 13 operations and runs \latOneRatioHB$\times$ slower than Sequential. Counting the ATen
kernels those operations execute gives an equally good fit ($R^2=\kernFitRsq$), so the effect is not an artifact
of how we count.\ifcompact\ Adding \texttt{nn.Module} calls as a second predictor gives $R^2=\opsModFitRsq$ (descriptive only;
six points).\else Adding the number of \texttt{nn.Module} calls as a second predictor explains almost all
remaining variance ($R^2=\opsModFitRsq$; roughly \perOpUs\us per operation and \perModUs\us per module call),
including the Sequential/Modular gap. With six architectures and three fitted coefficients, we treat this
decomposition as descriptive rather than predictive.\fi

\ifcompact
\textbf{Compilation.} With \texttt{torch.compile} (\cref{tab:arch}, comp.), the batch-1 spread narrows from
\eagerSpread$\times$ to \compSpread$\times$, but a fixed per-call cost of about 10\us makes the three-operation models slower;
\HB remains the slowest (\compRatioHB$\times$ Sequential).
\else
\textbf{Compilation.} \texttt{torch.compile} fuses each model's operations into one compiled graph (\cref{tab:arch},
column comp.). This narrows the batch-1 spread from \eagerSpread$\times$ to \compSpread$\times$
(\compModular--\compHB\us) and weakens the link to operator count ($R^2=\compFitRsq$), but it adds a fixed per-call
cost of about 10\us. The three-operation models therefore become slower (Sequential \latOneSequential\ to
\compSequential\us), while the operator-heavy hybrids become faster (\HA \latOneHA\ to \compHA\us). \HB remains the
slowest model (\compRatioHB$\times$ Sequential). For sub-kilobyte models at batch 1, compilation trades per-operator
cost for per-call cost rather than giving a free speedup.
\fi

\textbf{Batch size changes the ranking.} \Cref{fig:latency}\ifcompact\else a\fi\ shows two regimes. Up to a batch of about 64,
latency is nearly flat and ordered by operator count. Past roughly 500 samples, per-element work takes over
and the ordering reshuffles. At batch 4096, \HC becomes the \emph{fastest} model (\latBigHC\us vs.\
\latBigSequential\us for Sequential) despite having the most MACs. This is consistent with memory traffic
mattering more than arithmetic: \HC's widest activation is 20 values per sample, while Sequential's is 128 and
Parallel's concatenation writes 128 more. The two models that build intermediate concatenated tensors are the
slowest at batch 4096: \HB (\latBigHB\us) and Parallel (\latBigParallel\us). The latency ranking of these architectures therefore depends on the batch size at which it
is measured.

\ifcompact\else  % dropped in the 6-page build (4-thread panel not shown)
\textbf{Threads.} With four intra-op threads\ifcompact\else\ (\cref{fig:latency}b)\fi, batch-1 latency is unchanged. At larger batches the
effect is inconsistent. Sequential improves at batch 4096 (\latBigSequential\ to \threadSeqBigFour\us), but
Parallel at batch 1,000 slows from \threadParallelOne\ to \threadParallelFour\us and \HA at batch 4096 slows to
\threadHABigFour\us. For sub-kilobyte models, thread synchronization overhead can exceed the parallel work.
\fi
